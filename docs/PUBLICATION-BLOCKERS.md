## Executable sequencing and authority

The staged implementation replaces the old tag-triggered approval/build cycle:
prepare and attest once; authenticate separate immutable evidence E and genuine
GitHub decisions; authorize publishing only the approved bytes; observe real
tag/assets; and verify the detached receipt only after its producing workflow
has succeeded. No artifact, JSON document or commit must contain its own hash.
See [releasing](RELEASING.md) and the [protocol](adr/trusted-publication.md).

This is engineering infrastructure, not earned external evidence. All three
release execution-origin allowlists deliberately start empty because no genuine
reviewed producer is enrolled. Publication is denied until real authorized live,
complete benchmark and independently owned reproduction producers are reviewed,
pinned and executed. Each authenticated producer seal must cover its actual raw
evidence and transitive capability observations, not an unrelated signed marker.
Owner/reviewer approval cannot waive this missing execution provenance.

The fixed external read-secret names are `PUBLICATION_LIVE_READ_TOKEN`,
`PUBLICATION_BENCHMARK_READ_TOKEN` and `PUBLICATION_REPRODUCTION_READ_TOKEN`.
They are not evidence that any credential has been provisioned. After genuine
producer/code review and protected enrollment, the producer owner grants the needed
selected-repository Actions/artifact/attestation read access and the release
maintainer configures its matching secret through normal secret settings using a
secure handoff. Never paste credential values into chat or records. No external token
falls back to the publisher's primary token or local saved login; nonselected
GitHub credential variables are scrubbed from subprocesses. The
[runbook](RELEASING.md) distinguishes those read roles from actual write authority.

Typed capability records check actual argv, exit0, source-shaped results, concrete
targets, captured input/request identities and scoped consent/logs. Real render
proof still needs install/health/page/screenshot in successful Windows and Ubuntu
producer jobs. Job labels, hashes, a nonempty success object or an install marker
cannot earn that proof. Empty/partial provider data retain their honest limitations.
Current Bing cannot produce an accepted success while its source contract is
blocked; IndexNow202 only confirms receipt/pending validation, not crawling/indexing.

Prepared bytes, E and current decisions must remain fresh and bound to exact main
C. Keep E data-only, never execute/check it out, and do not merge it or advance main
before detached completion. The running complete job may attest only
`COMPLETION_OBSERVED`; a separate read-only consumer must authenticate the whole
successful exact producer attempt and recheck actual public bytes/current decisions
before `APPROVED`. A historical receipt cannot certify a later main or revoked
approval. No code cleanup, native scan claim, local EOS label, historical readiness
JSON, preparation or workflow dispatch replaces these real operations.

The August records stay historical. Existing basic mlmas HTTP evidence is neither
account authorization nor a full benchmark, browser proof, independent reproduction
or fresh final-role approval. Source tests, protected CI and preparation attestations
must not be described as those missing proofs. Internal readiness consistency
passing means a truthful BLOCKED record is consistent, not ready to release.
The documented workflows/helpers are engineering infrastructure, not proof of an
actual main PR, public release/tag, native security-scan/EOS certificate or complete
publication evidence. Preserve redaction and explicit site/account/request/time
and separate write-consent boundaries. Zero-spend permission stays zero; any paid
operation needs a separate approved budget and is not authorized by this document.
Missing actual inputs remain BLOCKED without weakening protections.
